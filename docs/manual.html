00The shape of it

One HTML file, one stylesheet, nineteen JavaScript files. No framework, no build step, nothing installed at runtime. What is in the files is exactly what runs in the browser.

Every test page is a hidden <section> inside the single index.html. Switching pages does not load anything — it shows one section and hides the others. That is why navigation is instant, and why the whole site works from a USB stick with no network at all.

The JavaScript files are numbered because the numbers are the load order. _boot.js loads first and exists only to make failures visible: if a script 404s or throws, it prints a banner on the page instead of hiding the problem in a console nobody opens. 00-core.js defines one global, TB, which holds everything shared — the router, the gamepad polling loop, the theme engine, the verdict renderer, the session results store. Every other file is a self-contained module that reaches into TB and never into another module.

The gamepad loop

One requestAnimationFrame loop in the core reads every connected controller sixty times a second and hands the readings to whoever registered interest. There is exactly one loop no matter how many pages you visit, and a test asserts that: two loops would read as a stuttering controller and would be very hard to trace.

why this matters to you

A controller is invisible to every browser until it sends its first input. That is a browser rule, not a fault with the pad. If a card stays dark, press a face button. Nothing in the app can work around it.

01Four rules it follows

These are not style preferences. Each one came out of a bug that reached the deployed site.

1. A result says what was measured, not what it implies

The earbuds page used to call a repeated serial “close to proof of a counterfeit” and style it as a failure. Testing one genuine pair twice flagged it the second time, every time — so the loudest result on the page was also its least reliable. Every verdict on the site now states what was measured and what that does and does not establish.

2. A test that cannot fail is worse than no test

The contrast check in the test suite gated at 2.6:1 for years. The accessibility standard is 4.5:1, so it could never have caught the two real failures that were in the stylesheet. It read as a pass and was not one.

3. Nothing outlives the page you left

The router tests once pulled 1.19 GB from ten clicks, and 1,094 MB of that arrived after the operator had navigated away. Every fetch now registers with an abort list, and leaving the page cancels the lot. The microphone and camera have the same discipline: both used to survive a page change with the status chip reading “off”.

4. Nothing leaves this machine

No server, no database, no analytics, no fonts from a CDN, no third party of any kind. The site makes zero requests to anyone but itself. That is also the shortest answer to give any IT department: there is no server to attack.

02Bench & report

The landing page. Shows what is plugged in, scores controllers the moment they connect, and turns the session into a printable QC record.

What it measures

Every device the browser will admit to seeing, live. Controllers get a full rest-state score on connection without you pressing anything.

It also collects every scored result from every page you visit, as you visit it.

How to read it

A dark card means the device has not sent input yet. Press a button on it.

Unit report: fill in the SKU, grade, your initials and any notes, then Build the report. Print it, save it as a PDF through your browser's print dialog, or Copy as text for a listing or an email.

What it cannot tell you

A device the browser cannot see is not necessarily broken — USB audio, printers and most storage never appear to a web page at all.

The report covers what you actually ran. It is not a certification and not a warranty.

The one thing to understand about the report

Every page of the app appears in it. The ones you did not open are printed under Not tested, in words, with what they would have covered. This is deliberate: a report listing only the tests you happened to run reads as a clean bill of health for the whole unit, and a buyer will read it that way.

One failure makes the unit Faulty however many other pages passed. A controller with a dead trigger is not eighty-six percent fine. Re-running a test replaces its result rather than adding a second row, so a unit can never be listed as both passed and failed.

be careful with this

Pasting the copied report into a spreadsheet is safe — a SKU beginning with =, + or @ is neutralised with a leading apostrophe so it cannot run as a formula. If you see that apostrophe, it is doing its job.

03Keyboard

Every key, chatter, rollover, and a typing test. Capture mode holds the keys that would otherwise throw you out of the page.

What it measures

Which physical keys register, how many simultaneous presses the board reports (rollover), whether a key fires twice from one press (chatter), and typing speed and accuracy.

How to read it

Press every key until the whole board is green. A key that never lights is dead or the layout is wrong — check the layout selector first.

Chatter is the fault that gets a board returned: it types aa when you pressed a once.

What it cannot tell you

Switch feel, actuation force, or how many more presses a switch has in it. Nothing in a browser reaches that.

Media and brightness keys are handled by the operating system and often never reach the page at all.

Capture mode

Holds Win, Alt+Tab, Esc and the F-row so they register here instead of switching windows. Hold Esc for one second to leave, or Ctrl+Shift+Q.

The lock keys — Caps, Num, Scroll — are detected without being allowed to toggle, so testing a keyboard no longer leaves Caps Lock on.

Ctrl+K still works in capture mode, which is the only way to reach another page while the keyboard is held.

04Mouse

Nine tabs. Buttons, click speed, double-click, scroll, tracking, polling rate, CPI, reaction time, drag, and the raw event stream.

What it measures

Which buttons register and in what order. Click interval, to catch a switch that double-fires. Scroll direction and granularity. Reported polling rate. Pointer travel against the surface, to estimate CPI.

How to read it

Double-click chatter is the common fault: two clicks logged from one press, with an interval under about 50 ms. That is a worn switch.

Side buttons that a driver has mapped to Copy/Paste or Back/Forward are detected automatically and named — this works for Razer Synapse, Logitech G Hub and the rest.

What it cannot tell you

True sensor CPI. The browser reports the operating system's pointer movement, after acceleration and scaling. Use the CPI tab as a comparison between mice, not as an absolute.

Polling rate is the rate the browser observed, which a busy machine will understate.

hold back/forward

A mouse whose side buttons the browser reports as real Back and Forward navigation needs the Hold back/forward button pressed before those presses can be counted. It traps the browser's own Back button while it is on, so it does not arm itself — an earlier version did, and that quietly broke Back across the whole site for the rest of the session.

05Controllers

Any pad the Gamepad API will report: Xbox, DualSense, Switch Pro, and the long tail of third-party and leverless controllers.

What it measures

Stick rest position and drift, deadzone, full travel on every axis, every button and trigger including analogue travel, and the D-pad however the pad reports it.

On connect it takes a two-phase rest sample: 450 ms to settle, then 850 ms to measure.

How to read it

Drift is a stick that does not read zero at rest. Small is normal; a reading that wanders while the pad sits still is the fault people return.

Work every axis to its limits so the travel bars fill. An axis that never reaches full is a worn or dirty potentiometer.

What it cannot tell you

Battery health, firmware version, or anything over the pad's proprietary protocol. Rumble can be triggered but not measured.

A wireless pad often appears twice — once as the dongle, once as itself. The page remembers which one actually sends input.

why the settle delay exists

The rest sample used to begin the instant the pad appeared — which is the moment you pressed the button that made the browser reveal it. Every controller was therefore scored with a button held down, and reported “button pressed early” on connection. The two-phase sample waits for your hand to leave.

06Joy-Cons

Reads Joy-Cons over WebHID, which gets at things the Gamepad API does not expose.

What it measures

Sticks and buttons, battery level, and the factory and user calibration data read directly out of the controller's SPI flash.

How to read it

Joy-Con stick drift is the known fault. Compare the live stick reading against the stored calibration centre: a large gap is drift the controller itself has not corrected.

What it cannot tell you

It is read-only. There is no firmware write path here, so it cannot recalibrate or repair a drifting stick — only show you that it drifts.

Needs a Chromium browser. WebHID does not exist in Safari or Firefox.

07Wheels

Racing wheels and pedal sets. Logitech G29 and G923, Thrustmaster, Fanatec — anything that presents as a gamepad.

What it measures

Steering travel lock to lock, throttle, brake and clutch separately, shifter and paddle positions, and every face and rim button, colour-coded by family.

How to read it

Turn the wheel fully each way. The steering bar should reach both ends and return to centre.

Press each pedal to the floor. A pedal that stops short of full travel has a worn potentiometer — the single most common fault on a used set.

What it cannot tell you

Force feedback strength cannot be measured, only triggered. Gear detection depends on how the wheel reports its shifter, which varies by model.

how the steering axis is found

Earlier versions assumed steering was axis 0. On a G923 it is not, so the wheel appeared not to turn at all. The page now watches every axis and picks the one with the widest travel whose midpoint sits near centre — and if it still guesses wrong, you can pick the axis by hand and it stops guessing.

08Mic & headsets

Microphone metering, headset output, a loopback test, and a music library for listening to real material.

What it measures

Live waveform and spectrum from the microphone, with peak, noise floor and clip count. Channel count and sample rate. Output through each earcup separately.

How to read it

Clip count above zero means the signal is hitting the ceiling and distorting — back the gain off or move the mic.

Loopback: the page plays a tone through the headset and listens for it on the microphone. “Both halves work” means the cable and both drivers are good. Put the headset on the bench, not on your head.

What it cannot tell you

Absolute sound pressure level. There is no calibrated reference, so the levels are relative.

It cannot judge sound quality. It can tell you a driver is silent, distorting or wired to the wrong side.

Sweepa tone that climbs through the frequency range — listen for gaps, buzzes and rattles
Basslow tones, for a driver that flaps or a loose enclosure
Pink noiseequal energy per octave; the best single signal for hearing a hole in the response
Patternsfive synthesised test pieces — drop, snap, walk, air, swing — for stereo imaging and transients

The music library

You can add your own .mp3 files, and only MP3. The check is not the filename: the page parses the MPEG frame headers, computes each frame's length from its own bitrate and sample rate, and requires three frames to chain at the computed offsets. Seventeen other formats are named explicitly, so a renamed .m4a is refused with a message saying what it really is.

Caps are 40 MB per file and 400 MB in total. Files are stored only on this machine and never uploaded. No music ships with the site — a build check fails if any audio file appears in the repository.

09Earbuds

The hardest page to do honestly. An acoustic fingerprint, a wear-detection check, a serial check, and a log.

What it measures

Acoustic fingerprint: the shape of the frequency response across 32 bands from 100 Hz to 12 kHz, compared against a reference pair you recorded yourself. Shape, not level — so how loud you set it does not matter.

Serial check: the structure of the serial, offline.

How to read it

Average deviation under 3 dB means these drivers behave like your genuine pair. 3–6 dB could be placement — re-seat and run again. Over 6 dB is a bigger gap than re-seating usually explains.

You must record a reference from a sealed known-good pair first, in a quiet room. Without it there is nothing to compare against.

What it cannot tell you

It cannot confirm a pair is genuine. It compares drivers, and nothing more. Treat it as one strong signal among several, never as proof on its own.

It cannot read a serial number, firmware or anything from Apple. No browser can.

The serial check, and exactly what it proves

Apple's older serials are structured. The 12-character format encodes the factory in positions 1–3, the half-year in position 4, the week-within-half in position 5, and the model in 9–12. The older 11-character format carries the year digit and week as plain digits. Serials issued from 2021 onward are 10 characters and deliberately random — no factory, no date, nothing to decode.

So the page can check a serial against itself: is it a length and character set Apple uses, do the date characters decode to a real half-year and week, and does the decoded build date make sense for the model you picked. That last one is the strongest thing here. A serial decoding to 2018 on a pair of AirPods Pro 2 is impossible — that model did not exist until September 2022. So is a randomised 10-character serial on a 2016 product. Those are contradictions, not opinions.

read this once

A serial that passes is not proven genuine. A correctly-shaped serial is as easy to print as a wrong one, and counterfeiters print them. A pass means move on to the next check. A fail is worth acting on.

For the authoritative answer, use Copy & open Apple's checker and read it from Apple yourself. The page cannot ask on your behalf: Apple's coverage checker sits behind a captcha placed there to stop exactly that, and a scraper would fail silently the first time they changed the page — answering “could not verify” for genuine pairs with nothing to distinguish that from a fake.

Wear detection

All the page can observe is that something paused playback. Genuine buds do that when you take one out. So does a Bluetooth dropout, an output-device change or a phone call — the event is identical and the browser cannot say which happened. Repeat it two or three times: pausing every time you remove a bud and never when you leave it alone is the pattern worth trusting. One pause is not.

The serial log

A memory aid, not a verdict. The usual reason a serial comes back twice is that you are re-testing the same unit, so the log counts the repeat rather than flagging it. It only points at a fake when two different physical pairs carry the same serial. Capped at the last 500 entries, stored only on this machine, with its own clear button.

10MIDI

MIDI keyboards and controllers over Web MIDI. 88 keys, velocity, and the continuous controls.

What it measures

Every note on and note off with its velocity, across the full 88-key range. Pitch bend, modulation and sustain. Stuck notes.

How to read it

Key shading follows velocity, so a key that always reads low has a weak or dirty sensor. Anything under 45 on a normal press is flagged.

A note still held after 6 seconds with your finger off it is a stuck note — the fault that makes a keyboard unusable.

What it cannot tell you

Key weight, aftertouch feel, or anything about the sound the keyboard makes on its own. This reads the MIDI messages, not the instrument.

Requested without SysEx, so it cannot read or change device settings.

11Monitors

Eleven solid colour fields and ten patterns, full screen, with an automatic run that walks all of them on its own.

What it measures

Dead and stuck pixels, backlight bleed, near-black crush, near-white clipping, banding, geometry and overscan, 1 px sharpness, panel uniformity, inversion, gamma, ghosting, and the live refresh rate.

How to read it

A dead pixel stays black on every field. A stuck pixel stays one colour on every field. Dust wipes off; a fault does not.

Dwell matters: 1 s is a fast sweep for catching a dead pixel or a backlight fault. 6 s is the right dwell for banding, uniformity and near-black crush, which your eyes need a moment to settle into.

What it cannot tell you

Colour accuracy. That needs a colorimeter — no screen can measure itself.

Brightness in nits, contrast ratio, or response time in milliseconds.

the stuck-pixel flush

It flashes the whole screen through saturated colours at two changes a second, which is under the three-per-second limit in WCAG 2.3.1. Under the limit is not the same as safe for everyone: if anyone nearby is photosensitive or has epilepsy, do not run it while they are in the room.

It arms on the first press and runs on the second, so it cannot be started by a mis-click or by a double-click from the faulty mouse currently on the bench. An earlier version ran at 5 Hz while telling the operator it was “well below” the seizure threshold. It was above it.

12Webcams

Live preview, resolution, frame rate and a snapshot.

What it measures

The resolution actually negotiated (it asks for 1920×1080 and reports what it got), measured frame rate, and the camera's reported name.

How to read it

A camera that negotiates far below its advertised resolution is either not the model it is sold as or is being limited by the cable or hub.

Frame rate well under the reported figure usually means poor light, not a fault — most webcams drop frames to compensate.

What it cannot tell you

Lens sharpness, colour accuracy or low-light performance in any measurable way. Look at the preview and judge.

the camera goes off when you leave

Leaving this page releases the camera. That used to be an empty function with a comment claiming it already did — the webcam stayed live for the rest of the session with the status chip reading “off”. On somebody else's laptop that is not acceptable, so the chip and the hardware now agree.

13Touch

Touchscreens, trackpads and pen digitisers.

What it measures

Every simultaneous touch point, drawn where it lands, with a running maximum. Pen pressure and tilt where the digitiser reports them.

How to read it

Drag a finger across the whole panel. A dead zone shows as a gap in the trail — that is a delaminated digitiser.

The maximum point count tells you how many fingers the panel really tracks, which is often fewer than the specification claims.

What it cannot tell you

Whether the glass is cracked, or whether the panel will fail under heat. Touch registering is necessary, not sufficient.

14Routers

A speed test, a long soak and a connection load test. The soak is the one that catches the fault that actually comes back.

What it measures

Speed test: idle latency, download throughput, and latency measured while the download is running.

Soak: response time once a second for up to thirty minutes, with every dropout time-stamped.

Load test: up to 400 connections opened at once.

How to read it

The grade is the number to look at. Read on.

One red column on a five-minute soak is a router you send back. Works fine, then drops out ten minutes later, is the complaint that brings them to the counter.

Anything short of all connections answering is a finding — a failing NAT table chokes here the way it chokes on a house full of devices.

What it cannot tell you

Upload is not measured and cannot be. There is no server here to send data to.

It cannot isolate the router: it measures the router, the modem, the line and this machine's Wi-Fi as one chain. And it cannot exceed the shop's connection, so it will never prove a router does gigabit.

Latency under load, and why it is the point

A line can measure 200 Mbps and still be unusable for a video call. The moment traffic starts, a badly-behaved router buffers so deeply that every packet queues behind the download. That is bufferbloat, and it is the single most common cause of “the internet is fine but Teams keeps dropping”.

So the test measures response time idle and again under full load, with the same probe, and grades the gap rather than the absolute figure — a satellite link starts at 600 ms and is usable, while fibre climbing from 10 ms to 300 ms is not.

A+ / Aunder 30 ms of extra delay — holds up under load
Bunder 60 ms — slight queueing
Cunder 200 ms — calls will wobble during a download
Dunder 400 ms — calls will break up during a download
Fover 400 ms — unusable for calls while anything is downloading

Idle 14 ms and loaded 600 ms is a router you reject however good its download number looks. That is a router fault far more often than a line fault.

Measurement detail that changes the answer

  • The first 1.5 seconds are discarded. TCP slow-start and the CDN's first-byte latency make the opening of a run unrepresentatively slow, and including it understates a fast line badly.
  • Streams ramp from three up to eight while throughput is still climbing. One connection cannot fill a fast link; eight on a slow one just fight each other.
  • Jitter is the mean absolute difference between consecutive probes, not standard deviation — which reads deceptively low on a line that alternates fast, slow, fast, slow, the behaviour that actually ruins a call.
  • Every byte pulled is counted and shown, and everything stops the moment you leave the page.

Label each run — LAN port 1, 5 GHz, 2.4 GHz — and compare them in the runs table. Four runs and you have tested every port: a dead port shows as total loss, a bad one as dropouts the others do not have.

15Stress test

Sustained CPU and GPU load, to find the machine that passes a ten-second test and dies after ten minutes.

What it measures

Frame rate under continuous WebGL load, with the current and minimum figures tracked over the run. Worker threads loading the CPU in parallel.

How to read it

Watch for the frame rate falling away after a few minutes and staying down. That is thermal throttling: a blocked fan, dried thermal paste, or a heatsink that is not seated.

A machine that holds its frame rate for ten minutes is thermally sound.

What it cannot tell you

Temperatures in degrees. No browser can read a thermal sensor — the throttling is inferred from the frame rate falling, which is the symptom rather than the cause.

16System & privacy

What the machine reports about itself, the connection watchdog, and the panel that shows and deletes everything stored here.

What it measures

CPU threads, a lower bound on memory, platform, graphics chip from the renderer string, storage quota, and battery charge and charging state.

The watchdog time-stamps every device connection and disconnection.

How to read it

The connection watchdog is worth more than any score on the site. A device that appears and disappears in that log is a loose port or a failing cable — the fault that tests fine for ten seconds and comes back a week later. Leave it open with the device plugged in.

What it cannot tell you

Battery cycle count or design capacity. Browsers do not expose either, so battery health still needs the manufacturer's tool.

Memory is reported as a minimum and rounded by the browser on purpose, to make fingerprinting harder.

The privacy panel

It counts what is actually stored rather than listing what is supposed to be — every key, with its size, and the audio library with its real byte count. A key it does not recognise is reported as unaccounted for rather than ignored, so a future change that starts saving something cannot do it quietly.

Delete everything clears local storage, session storage and the audio database, then reads the store back and reports what is actually left. If another tab is holding the database open it says so and names the cause, instead of claiming a deletion that did not happen. Two presses, with a real gap between them, because this also throws away the earbuds reference curve.

19Security posture

The short version for any IT department: there is no server, so there is nothing to breach.

  • 0  third-party requests. No fonts from a CDN, no analytics, no scripts from anywhere but this site. Typefaces are the ones your operating system already ships.
  • CSP  default-src 'none' with script-src 'self'. No inline script, no eval. Verified enforced from inside a Worker, not just read off the header.
  • deny  Framing refused by header, by policy and by the page itself — because framed without headers, the microphone and camera permissions this page requests would be granted to whoever framed it.
  • least  Permissions-Policy grants microphone, camera, gamepad, HID, MIDI and fullscreen to this origin only, and denies USB, serial, Bluetooth, screen capture, geolocation, payment and topics outright.
  • 404  No source, documentation, build script or test file is deployed. They are excluded from the upload, not merely redirected.
  • index  robots.txt, an X-Robots-Tag header on every response, and a noindex meta. Twenty crawlers named individually, because several treat a wildcard as advisory. No sitemap.

Permissions are requested only when you press the button that needs them, and the browser asks you every time it has to. Revoke any of them from the padlock in the address bar; nothing here can grant itself access.

Eighteen test suites run against the site, including one that fails the build if an inline-script allowance, a dropped header, a committed secret, an audio file or a stale bundle appears in the tree.

20What no browser can do

Worth knowing in one list, so you never go looking for it.

  • Battery health. Cycle count and design capacity are not exposed. Manufacturer tool only.
  • Temperatures. No thermal sensor is readable. Throttling is inferred from frame rate falling.
  • True sensor CPI. You get the operating system's pointer movement, after acceleration.
  • Absolute sound level. No calibrated reference, so audio figures are relative.
  • Colour accuracy, brightness in nits, contrast ratio. A screen cannot measure itself.
  • Upload speed. Needs a server to receive the data. There isn't one.
  • Wi-Fi names, signal strength, the band you are on, the router's admin page or its firmware. Connect the machine to the port or band you want to check and label the run instead.
  • Anything from Apple about a serial. No public API, and their checker is behind a captcha placed there to stop automated queries.
  • USB audio interfaces, printers, most storage. They never appear to a web page.
  • Firmware, on anything. The Joy-Con page reads calibration; it cannot write it.

Everything on that list is a real limit of the platform, not a gap waiting to be filled. Where a test gets close to one of them, the page says so on its face rather than letting the number imply more than it measured.
